# Модуль «Онбординг»

Запуск нового клуба после продажи франшизы: план партнера по неделям (копия шаблона УК),
еженедельные звонки с протоколами, задачи, вехи, состояние «клуб открылся».
Онбординг продолжает воронку «Франчайзи» (`franchise_candidates`) и привязан к кандидату;
`partner_id` связывает его с клубом в CRM, чтобы партнер видел свой онбординг.

Модуль изолирован (модульный монолит): то же приложение и та же база, но свой код и своя схема.

## Где что лежит

| Путь | Что это |
|---|---|
| `src/app/onboarding/page.tsx`, `src/app/onboarding/[id]/page.tsx` | Тонкие маршруты |
| `access.ts` | Кто видит и кто правит (без зависимостей, работает и на клиенте) |
| `api.ts` | **Единственная** точка входа для остальной CRM |
| `actions.ts` | Серверные действия (каждое начинается с проверки роли) |
| `types.ts` | Типы строк схемы `onboarding` и расчет прогресса |
| `server/db.ts` | Единственное место, где код обращается к схеме `onboarding` |
| `server/guard.ts` | Проверка роли и права на конкретный онбординг |
| `server/load.ts` | Загрузка данных страниц |
| `components/` | Интерфейс: обзор, страница партнера, вкладки |
| `sql/onboarding_setup.sql` | Таблицы, права, RLS, шаблон и план Софии (запускался один раз) |

Вне модуля менялись только: пункт меню в `AppShell.tsx`, иконка `IconOnboarding` в `icons.tsx`,
ключи `navOnboarding` / `onb*` в `src/lib/i18n.ts`.

## Правила изоляции

1. Код только в `src/modules/onboarding` и `src/app/onboarding`.
2. Таблицы только в схеме `onboarding`. В `public` ничего не добавляем.
3. Связь с CRM только внешними ключами: `franchise_candidates`, `partners`, `auth.users`.
4. Другие разделы не читают таблицы `onboarding` напрямую, только через `api.ts`.
5. Доступ: hq правит все; partner видит свой онбординг, отмечает статусы пунктов и задачи
   своей стороны; viewer только смотрит. Проверка в меню и на сервере (страница + каждое действие).
6. Интерфейс из общих классов темы (`bg-background`, `border-border`, `shadow-card`, `text-muted`…).

## Таблицы (схема `onboarding`)

- `template_weeks`: недели шаблона (`w1`..`w10`, `rhythm` «Регулярный ритм», `school` «Школа мастеров»).
- `template_items`: пункты шаблона УК (блок, материал, действие, тип, кто доносит, теги, `link_mode`:
  `template` оригинал УК / `copy` копия партнеру / `none`, `template_url`).
- `onboardings`: онбординг партнера (кандидат, клуб, город, старт, куратор, день звонка, текущая
  неделя, `status` onboarding/opened, `opened_at`, папка на Диске, следующий звонок).
- `plan_items`: план партнера = копия шаблона (статус todo/progress/done/moved, дата, ссылка на
  копию файла, `custom` свой пункт, `hidden` убран у партнера).
- `milestones`, `meetings` (цифры недели, пройдено, заметки), `tasks` (сторона partner/hq, срок).

Чтение через RLS (`can_view_network()` или свой `partner_id`), запись только service_role
из серверных действий после проверки. Схема включена в Data API → Exposed schemas.

## После открытия клуба

Кнопка «Клуб открылся» (hq): наверху «Звонки и протоколы», «Задачи», «Регулярный ритм»;
план онбординга уходит в конец как архив. «Вернуть в онбординг» откатывает.

## Следующий шаг

Кнопка «Начать онбординг» сама создает папку партнера на Google Диске и копирует туда
пункты с `link_mode = copy`, ставя ссылки в `plan_items.file_url`. Нужен сервисный аккаунт Google.

## Как вынести модуль в отдельное приложение

Перенести папку `src/modules/onboarding` и маршрут `src/app/onboarding` во второе приложение
с общим пакетом интерфейса. Схема `onboarding` остается в той же базе, вход тот же.
